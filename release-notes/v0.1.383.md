## Feature: pipeline stages ask the Anchors before they run

A release stage ran on a sha no review had seen, because nothing the workflow consulted said it
should not (MIF). `pipeline:` declares the stages a pipeline asks about: the branches each runs
on, the conditions its sha must meet, and the command that validates it.

```yaml
pipeline:
  stages:
    review-release:
      branches: [review]
      requires: [flow, { gates: ci }]
      verify: node scripts/smoke-review.mjs
    production-release:
      branches: [production]
      requires:
        - flow
        - any: [{ passed: review-release }, { from: "hotfix/*" }]
      verify: node scripts/smoke-prod.mjs
```

The three commands, through the `gh` CLI with `GH_TOKEN`:

- `anchors pipeline can-run <stage>` is the first job; the stage's other jobs need it. It refuses
  a stage that is not declared, a branch the stage does not run on, and a requirement that does
  not hold, naming each.
- `anchors pipeline done <stage>` is the last job. It runs `verify:` and records the outcome on
  the sha as the commit status `anchors/pipeline/<stage>`.
- `anchors pipeline run <stage>` does can-run, `run:`, `verify:` and the record in one step.

The requirements:

- `flow`: the sha is the merge of a pull request `branch_flow:` allows.
- `gates: <phase>`: the phase's gates pass.
- `passed: <stage>`: the head the sha was merged from carries that stage's success.
- `from: <branch>`: the sha was merged from that head.
- `any:`: one of several holds.

The `pipeline-wired` gate, declared with `scope: project`, reads `.github/workflows/*.yml`. It
fails on four things:

- a call to an undeclared stage;
- a declared stage no workflow calls;
- a stage asked and never recorded;
- a workflow that calls no stage and is not under `pipeline.unguarded`.

A project with no `pipeline:` sees no change.
