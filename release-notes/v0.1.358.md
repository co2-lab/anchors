## Handles built on the caller's head: measured, or pending — never green

A component often builds its testID from the id its caller passes in, for example
`` `${testID}-option-${opt.value}` ``. The `exposed` patterns only read a template that
starts with a literal, so such a unit looked like it exposed nothing. `testid-consistent`
and `section-required` then passed without measuring anything.

- **The `suffix` group.** `dialect.test_handles.exposed` now accepts a `suffix` group: the
  segment the unit adds to its caller's head. The ts example reads it, so copy this pattern
  into your own:

  ```yaml
  - 'testID[a-z]*\s*[=:]\s*\{?`\$\{[^}]*\}(?P<suffix>[^`$]*)'
  ```

- **How a derived handle is checked.** The handle becomes `*-option-*`:
  - the component's spec declares it as written, in Test IDs;
  - a test or flow queries it by naming the segment after a head, such as `:pay-option-a`;
  - the caller's own handle (`:pay`) counts as queried through a segment that some unit of
    the project derives. A segment that no unit derives counts for nothing, so
    `:pay-other` does not query `:pay`.
- **Handles built from values alone.** `${prefix}${key}` and `${prefix}-${i}` leave the
  segment naming nothing. The gates report them as pending, with the file and line, and
  never pass them. Give the handle a literal segment.
