## Feature: the branch flow — which branch merges into which

A release flow goes one way, and nothing said which. At MIF, commits went on the production
branch and the review branch was aligned from it, the flow run backwards, and nothing noticed.

`branch_flow:` declares it: for each base branch, the heads a pull request may merge into it,
and the branches that take no commit of their own.

```yaml
branch_flow:
  merges:
    review:     [develop, "hotfix/*"]
    production: [review, "hotfix/*"]
    develop:    [review, production, "hotfix/*"]
  protected: [review, production]
```

A branch is a glob whose `*` does not cross `/`, or a regular expression after `re:`.

- `anchors branch check`, on the pull request event, refuses a pair the flow does not allow.
- On the push event, it refuses a push to a guarded branch that is not the merge of an allowed
  pull request. It asks GitHub through `gh` with `GH_TOKEN`. This covers a repository with no
  server-side protection, such as a private one on GitHub's free plan.
- On the machine, the pre-commit and a new pre-merge-commit hook refuse a commit on a protected
  branch (`anchors branch guard`). Run `anchors install-hooks --force` to get the new hook.

A project with no `branch_flow:` sees no change.
